## Q1: media-upload のストレージバックエンド選定

**Answer**: S3 互換。開発環境は compose.yml に **RustFS** を追加して統一する。

**補足**: Q0 の回答により「ShuttlePub 側で保持」の選択肢は本体非存在のため脱落。
NFR「差し替え可能な抽象化」(features/media-upload/requirements.md)は維持し、
第一実装を S3 互換とする。ローカル FS バックエンドは抽象化の第二実装として
将来追加可能な位置づけ。

**開発環境実装の選定経緯**:
- MinIO: OSS は 2025-12 メンテナンスモード宣言・2026-04-25 リポジトリ正式
  アーカイブ済みのため却下
- LocalStack: AWS 全体のエミュレータで S3 用途にはヘビーのため却下
- Garage: 有力候補だったが「compose 起動時の自動設定が難しい」との懸念を調査。
  その情報は v2.3.0 (2026-04-16) 以前のもので、v2.3.0 の `--single-node` +
  `--default-bucket` フラグで全自動化可能と判明。成熟度高く本番セルフホストにも
  使えるが、forcePathStyle 必須・ACL/バケットポリシー非対応・コンソールなし
- RustFS (採用): 1.0.0-rc.1 (2026-08-08)。環境変数のみで起動 (CLI 初期化不要)、
  Podman 公式サポート、Apache 2.0、Web コンソール内蔵、MinIO 互換 env エイリアス
  あり。S3 API は 452 テスト済みで multipart/presigned URL もカバー。
  RC 段階・分散モード未リリース・サードパーティ評価は本番非推奨だが、
  開発環境 + CI 用途では許容範囲と判断。本番ストレージ選定は抽象化レイヤで
  後から差し替え可能なため、本 packet のスコープ外とする

## Q2: 画像の配信ドメイン・配信方式

**Answer**: 別ドメイン直接配信。Emumet はストレージをプロキシしない。

**確定内容**:
- 配信 URL は「公開ベース URL + オブジェクトキー」で生成し、ベース URL は
  設定で差し替え可能とする
- 本番は Cloudflare R2 + カスタムドメイン接続を想定。R2 カスタムドメインは
  Cloudflare のエッジキャッシュ経由で配信されるため、別途 CDN 製品は不要
  (= これが CDN 構成)。R2 はエグレス料金ゼロで CDN 配信と相性がよい
- 開発環境は RustFS エンドポイント直結
- presigned URL は採用しない (AP の icon/image URL はリモートサーバーが
  後から再 fetch するため、期限付き URL は不適)

**プロキシ配信との比較検討メモ**:
- プロキシの利点は URL 永続性・バケット非公開化・アクセス制御・運用集約だが、
  AP メディアは公開前提のためアクセス制御の利点は薄く、URL 永続性も
  カスタムドメインを自前管理すれば直接配信で確保できる
- 負荷面 (全メディアトラフィックが Emumet 経由になる) を重視し直接配信を選択

## Q3: アイコン/バナー変更時の Update アクティビティ配送

**Answer**: 配送する。

**確定内容**:
- アイコン/バナー変更時に Update(Person) アクティビティをフォロワーの inbox へ
  署名付き配送する (連合標準挙動。Mastodon 等と同じ)
- 実装は既存 `delivery.rs` (application/src/service/activitypub/delivery.rs) を
  流用可能であり、deferred 中の C2 (post-relay) には依存しない
- 対象はフォロワーの inbox への配送のみ。リレーサーバー経由の配送は
  post-relay 側スコープ
