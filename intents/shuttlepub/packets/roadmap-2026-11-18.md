## 今の実態 (2026-11-17)

画面と契約が先行していて、中身 (ShuttlePub 本体とサービス間の接続) が空いている。

- [SP] `dev` で Follow→Accept と `GET /actor` だけが動く (保存なし)。`/api/v1` の 15 操作は
  すべて 501。通常投稿の作成・コミュニティ TL・公開範囲は契約にもない。
  `shuttlepub-relay-follower` (#32) が進行中 (2026-11-20 に retired。P1 の項を参照)。
- [FE] 認証・Profile 選択・Emumet のドメイン設定は real。TL・投稿・反応・検索は mock だけで、
  `createPost` は常に未実装。`TimelineKind` は HOME / LOCAL / FEDERATED の仮置き。
- [EM] アカウントの ES/CQRS、Ory、組織、モデレーション、登録ゲート、Profile 単位の連合
  (actor・鍵・Follow/Block の送受信) まで動く。inbox は Create/Like/Announce を受けて
  捨てている。署名 API・link (post-relay / shuttlepub-link) は packet になっていない。
  リリースの仕組みは `emumet-release-container` (Emumet #110) で着手済み。
- [BS] Drive 本体と web は動く。Emumet との連携・media-metadata は契約設計のみ。

## P1 連合の土台

現行の Ory 構成 (Kratos / Hydra) のまま進める (D36)。ShuttlePub は連合先に公開する
リレー用の inbox と、Emumet からの転送を受ける専用 API の両方を持つ (D39)。

- [SP] nitinol 0.8 + PostgreSQL の導入と、連合を申し込んできたサービス (供給元) の受け入れ・
  届いた投稿の受け入れ (D48)。`shuttlepub-relay-follower` (#32) は設計を見直して retired にし、
  PR #33 は merge せずに閉じた (2026-11-20)。新しい実行単位で作り直す。Global TL は後のフェーズ
- [SP] Undo・Announce の転送・配送キューと再試行 (D20 のまとまり A)
- [EM] ホームの link の最小部分 (信頼モード③だけ、本人による API 登録、D31・D56)。内向き転送の転送先に必要なので
  shuttlepub-link から P1 に前倒しする (2026-11-18 の P1 分解で判明)
- [EM] inbox の Create などを捨てずに、ホーム (と信頼モード②以上の link) の ShuttlePub へ
  転送する (post-relay、D30・D54・D55)
- [SP] 転送の受け口: 専用 API で受け、重複を除いてイベントとして保存する
  (envelope の形は上と共有、D54)
  - **完了条件 (D68)**: この受け口の完了には、Emumet の `POST_RELAY_INBOX_ENABLED=true` への切り替えを含める。
    受け口 (`POST /internal/v1/emumet/activities` の受信・検証・重複除去・保存) を実装・デプロイしたら、
    Emumet 側の準備 (HTTPS の `PUBLIC_BASE_URL`、サーバー鍵、転送先として許可する origin、承認済みのホームの link、
    容量の確認。Emumet の `docs/post-relay-inbox-intake.md`) を確かめ、連合 E2E を通したうえで、
    Emumet の `POST_RELAY_INBOX_ENABLED` をオンにする。オンにするまでこの項目は完了にしない。
    Emumet の初回リリース時点で受け口がそろっていれば、リリースと同時にオンにする
    (Emumet 側の完了条件は [Emumet backlog](../../emumet/packets/backlog.md) の `emumet-first-release`)。
- [SP/EM] 転送時の認証 (D51): Emumet のサーバー単位の鍵で転送リクエストに署名し、ShuttlePub が
  公開鍵を取得して検証する (P1 で Emumet のサーバー鍵の生成・公開も実装)。受信・キュー・転送・保存は
  Ory に依存しない (再送は D30 の 72 時間)
- [EM] ログイン・同意 (Hydra の Login / Consent Provider) とクライアント登録 (DCR) の
  境界を分け、あとで Stellar へ移せるようにする (D38・D52)。P1 では DCR を実装せず、境界の規則と
  既存のログイン・同意のモジュール分離までとする (D52)
- [全体] イメージ公開 (D35・D53)。`emumet-release-container` は `v*` タグからの公開のみ。
  Emumet の dev からの公開 (タグ: コミット SHA と dev) は初回リリースと同時に `dev` ブランチを
  新設してから始める (D53)。ShuttlePub も同じ形で公開する
- [新 repo] 連合 E2E (D35。初回リリース前の Emumet イメージの用意の仕方は E2E の設計で決める、D53)
  - D68: この連合 E2E が通ることは、Emumet の `POST_RELAY_INBOX_ENABLED` をオンにする条件の 1 つ (オンにする作業は上の「転送の受け口」の完了条件)。

完了の目安: 外部の ActivityPub サーバーから届いた Activity を Emumet が受信し、
Profile のアタッチ先の ShuttlePub へ転送し、ShuttlePub が重複を除いて保存する (D36)。

## P1 の後: Stellar の切り出し (D36・D37)

P1 の連携が通った後に行う。外部公開・本番デプロイに対してどの時点で切り出すかは、
外部公開後に変えにくい契約と移行コストを確かめてから決める。

- [新 repo / Stellar] Ory の上に載る薄い認証サービス。初期スコープの候補は
  ログイン・同意のコールバックとクライアント登録 (DCR) の受付。機能の追加は最小限
- 未決: Stellar を Emumet ごとに置くか共有するか、ログイン主体と Emumet の Account の
  対応、D32 の対応表の担当 (D52)、OpenID Federation の trust anchor
