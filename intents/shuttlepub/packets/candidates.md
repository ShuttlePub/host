## 共通の分割方針

- D01–D17 は意図候補 ID。既存の決定記録の D 番号とは別の名前空間。
  1 候補をそのまま 1 実行 packet にしない。契約整理後、target repo ごとに
  独立して検証できる最小単位へ分割し、producer の契約と consumer の接続を分ける。
- SNS UI の primary domain は暫定で shuttlepub、実装先は
  `ShuttlePub/shuttlepub-frontends`。既存 ratcap domain はフロントエンドモノレポの
  歴史的記録を持つが、本一覧の全文を複製しない。必要な実装 packet から参照する。
- 既存 Note / reply / turbo / turbo_quote / reaction / timeline 基盤を拡張対象にする。
  現在の main の観察は [意図の正本](../product/social-experience.md) を参照し、
  2026-08-29 の旧実装インベントリを現在の機能欠如の根拠にしない。
- Note の連合送受信、認証接続、永続化等の土台は別の依存として確認する。
  各候補にまとめて再実装する前提を置かない。

## D01 — contextual-commentary

- **意図**: [I01](../product/social-experience.md#i01)。文脈を追いたい読者が、独り言に至るまでの
  投稿・リポストを大きな負担なくたどれる体験を中心にする。
- **grillで採用済みの方向**: [正規記録](../interviews/discord-feature-grill-2026-10-15.json)の
  `d01-q01-context-over-repost-appearance`を`d01-q02-low-effort-chronological-context`で具体化。
  低負担で文脈を追えれば方式は問わず、前回の「リポストっぽさ」という表現から導く表示禁止・主従は独立要件にしない。
  元作者への普通の RT 表示は原案の方式仮説として履歴に保持し、必須の受入条件にしない。
  初回の閲覧導線はQ3、リモート履歴補完の範囲はQ5で採用する。
- **候補の状態**: 主要な利用意図は整理済み。リモート取得・ページング等の取得/API契約は検証待ちで、
  実装readyとはしない。candidate・queue未登録・issue未公開・仮slug未予約を維持する。
- **仮 slug**: `contextual-commentary`。
- **初回の閲覧導線として採用済み**: `d01-q03-history-direction-controls`。開いた投稿を起点に、
  前後の投稿・リポストをたどる。過去は下側に表示し、下への無限スクロールで続きを取得する。
  新しい方は上に専用ボタンを置き、押下時に取得する。新しい方のスクロール自動取得・定期ポーリングは追加しない。
  専用引用・明示的な紐付け機能を必須にしない。Misskey・iceshimpはユーザーの体験例であり、
  指定された動作以外の現行実装を採用・検証済みとはしない。
  `d01-q04-context-actor-on-repost`で、通常投稿を直接開く場合は同じ投稿者、タイムラインのリポストから
  開く場合はリポストした人の履歴とする。後者を元作者の履歴へ自動切替しない。
  元投稿の作者表示・操作権限はリポストした人のものへ置き換えない。
- **初回のリモート補完として採用済み**: `d01-q05-remote-history-initial-scope`。相手サーバーの取得可能な
  公開投稿・リポスト履歴を初回から補い、自サーバーに未着の前後の文脈もたどれるようにする。
  [D06](#d06)の投稿履歴取得部分を共通契約・依存とし、関係一覧取得・フォロー等の操作は抱き合わせない。
  相手の公開範囲・取得能力・保存状況に制約され、全peerの完全履歴を保証しない。
  非公開履歴の取得・公開範囲の回避、全件一括取得、常時同期を必要条件にしない。
- **target repo 別分割**: ShuttlePub で起点前後のユーザー投稿・リポストの取得範囲、順序・ページングの
  契約を確認する候補。D06と共通のリモート投稿履歴取得契約を分ける。
  frontends で投稿詳細の下側無限スクロール・上側ボタン取得、部分取得等の状態表示を扱う候補。
- **最小受付・検証案**: 起点の前後に投稿・リポストがある例を使い、過去は下へのスクロール、
  新しい方は上のボタン押下で取得され、読者が大きな負担なく文脈をたどれるか確認する。
  AがBの投稿をリポストした後でAが独り言を書いた例で、そのリポストを開き、上側ボタンから
  Aの後続投稿をたどれることを確認する。
  対応peerの未着の公開投稿・リポストが補完されて文脈をたどれる例を含める。
  取得不能・部分取得・終端を区別し、未取得を履歴なしと誤表示しないことを確認する。
  作者への通常 RT 表示や特殊な通知・専用引用配送は合格条件にしない。
- **依存**: ユーザーの投稿・リポスト履歴取得、閲覧権限、順序・ページング、投稿詳細の表示契約。
  D06と共通のリモート投稿履歴取得部分を依存とし、D06の関係一覧・フォロー操作全体は依存にしない。
  専用引用配送や特殊な作者通知を必須依存にしない。
- **設計・検証が必要な事項**: 取得件数・カーソル・境界・重複・同時刻・リポスト時刻、
  読み込み中・失敗・終端表示、viewport位置保持、ボタン再取得時の具体挙動。
  誰のどのリポストから開いたかを画面遷移と取得APIで保持し、起点時刻・活動ID・カーソル等を設計する。
  原投稿の作成時刻ではなくリポスト時刻を使う等の詳細はユーザー決定にしない。
  リモート取得方法・対応peer・ページング・キャッシュ・失敗時の再取得、取得不能・部分取得・終端の
  区別を設計・検証する。補完時も活動文脈と上下導線を維持し、重複・順序崩れ・起点喪失を検証する。
  製品別API・ActivityPub・スクレイピング等の具体手段を採用した記録ではない。
- **未決事項**: リポストの文脈がない直接リンク、元作者への任意の履歴切替、複数回リポスト等の境界事例。
  原案の時系列的前後取得・リンクを自動引用にしない方式も履歴として保持する。
  特別な作者表示・通知、秘密保持、明示的な紐付けを追加要件にしない。
- **既存との関係**: 投稿詳細・ユーザー履歴の既存基盤を確認し、必要な拡張範囲を判断する。
  [初動決定](../decisions/2026-08-29-initial-shaping.md) D5/D7 の語彙・機能を尊重する。
  D13の引用・リポスト等の許可分類との対応は、D01で操作を追加する方式を選ぶ場合に、その意味が決まった後で統合確認する。

## D02 — media-reuse-license

- **意図**: [I02](../product/social-experience.md#i02)。添付画像について他者が利用できる範囲を作者が示す。
- **利用条件の単位として採用済み**: [grill記録](../interviews/discord-feature-grill-2026-10-15.json)の`d02-q01-file-shared-license`。
  同じ画像fileには共通の利用条件を付け、各投稿から同じ条件を示す。投稿ごとに別条件を付ける方式は採用しない。
  ユーザー向けの適用／参照単位であり、保存正本・API・Booskiff配置まで確定する決定ではない。
- **指定方法として採用済み**: `d02-q02-preset-license-selection`。
  初回は用意されたプリセットから選び、「未指定」も選択できる。独自の文章／URLで条件を登録する方式は初回外。
  公式ライセンス原文への参照リンク表示は別で、禁止しない。
- **新規画像の初期値として採用済み**: `d02-q03-unspecified-default-license`。
  新しい画像fileで条件を選ばなければ「未指定」とし、CC等は利用者が選んだ場合に付ける。原案のCC BY ND既定は歴史的提案として保持するが現行初期値には採用しない。
  未指定はこの機能で追加許諾を示さない意味で、再利用全面禁止や既存許諾の取消しではない。既存file移行やカスタム既定値／前回継承は今回決定しない。
- **初回の選択肢として採用済み**: `d02-q04-initial-license-presets`。
  CC BY 4.0・BY-SA 4.0・BY-ND 4.0・BY-NC 4.0・BY-NC-SA 4.0・BY-NC-ND 4.0、CC0 1.0、未指定の8選択肢を用意する。
  CC0は6種のCCライセンスとは別の、法の許す範囲で著作権等を放棄するツールと区別する。初期値は未指定、選択時のみ付与し、既存fileへの一括適用は決定しない。
- **公開後の固定として採用済み**: `d02-q05-freeze-license-after-publication`。
  初回は公開時のfile共通条件を固定し、公開後の条件選び直し・未指定からCC等の追加を提供しない。
  固定は利用条件のみで、D11の画像タグ／センシティブ分類の編集可とは分ける。
  削除／再uploadによる過去の許諾取消し、管理者例外・他人の権利処理や画像実体の永久保存を採用したものではない。
- **固定する共有の範囲として採用済み**: `d02-q06-freeze-on-first-sharing`。
  フォロワー限定等も含め公開範囲を問わず、初めて他者向けの投稿で共有した時点でfile共通条件を固定する。uploadや公開URL生成だけでの固定にはしない。
  下書き／自分だけの投稿・送信失敗／予約／同時変更との整合や実装のlock時点は設計・検証する。
- **候補の状態**: 主要な利用意図は整理済み。保存正本・認可・固定処理・既存file移行・表示／連合契約は検証待ちで実装readyではない。
  candidate・queue未登録・issue未公開を維持し、実装packetへ自動昇格しない。
- **仮 slug**: `media-reuse-license`。
- **target repo 別分割**: Booskiff のファイルメタデータを第一候補とするが、先に
  ShuttlePub とfile共通条件の保存正本・添付からの参照／表示契約を決める。
  後続は Booskiff の保存 API、ShuttlePub の添付・連合写像、frontends の指定・表示に分ける。
- **最小受付・検証案（未実施）**: 許諾を指定した画像を添付し、閲覧側で同じ内容を確認できる。
  同じ画像fileをP1・P2に添付すると、両投稿から同じ共通条件を確認できる。
  8選択肢をそれぞれ保存・表示でき、未指定とCC0を取り違えず、任意文章／URLの入力を初回の必須手順としない。管理操作はこの検証案で確定しない。
  未選択の新規fileは未指定でCCを自動付与せず、利用者が選択した場合に各投稿で共通条件が表示されることを確認する。
  初めての他者向け投稿が限定共有でも未指定／選択条件が固定され、以後は未指定からの追加を含め変更できず、同file再利用でも同じ条件を示すことを確認する。
  固定対象は利用条件だけで、タグ／センシティブ分類の編集を固定しない。実装のlock時点や下書き等の境界例はこの検証案だけで確定しない。
- **依存**: Booskiff ファイル参照・メディア添付契約。D11 とメタデータ構造を共有できるか確認する。
- **未決事項**: 保存正本・API／参照契約、指定権限・権利者表示と認可、下書き／自分だけの投稿・送信失敗／予約／同時変更と固定処理の整合・実装lock時点、
  既存file移行、表示／外部配送契約、同一bytes別fileの自動統合・他人fileの権利処理。管理者の選択肢追加／例外、既定値カスタム設定／前回継承も今回採用しない。
  公開後の条件変更・変更履歴・既存投稿への更新波及は初回外とし、後続の採否／契約は未決。
- **一次資料の確認（2026-10-19、仕様採用ではない）**: [CC BY-ND 4.0公式説明](https://creativecommons.org/licenses/by-nd/4.0/deed.ja)は、条件を守った営利目的を含む複製・再配布を認め、許諾者はその自由を取り消せないとする。改変した資料の頒布は認めない。
  既定値や後変更を検討する前提として保持し、条件表示の変更で既に与えたCCの許諾を撤回できると扱わない。今回CC BY-ND 4.0の採用や具体的な変更UIを決定したものではない。
- **後続の採用と補足調査（2026-10-19）**: 上記はQ1時点の調査記録であり、その後Q4でCC BY-NDを含む初回の選択肢を採用した。公開後の変更機能はまだ決定していない。
  [CC公式FAQ](https://creativecommons.org/faq/#what-if-i-change-my-mind-about-using-a-cc-license)の撤回不可と既存条件での再配布継続、[CC0 1.0本文](https://creativecommons.org/publicdomain/zero/1.0/legalcode.en)第2・3項の法の許す範囲の撤回不能な放棄とfallbackを確認した。
  現在の条件表示を変える機能と過去の許諾／CC0の効果は区別し、以前に示した条件の記録・公開方法は別途整理する。
  この補足調査はQ4時点の記録で、現在の初回仕様はQ5の公開後固定。将来の変更機能や過去の許諾を取り消す決定へ流用しない。
- **既存との関係**: [Booskiff の使命](../../booskiff/identity/mission.md) のファイル管理を候補根拠にする。
  公開 / 非公開のアクセス制御と利用許諾は別の属性として契約を詰める。
  D11のタグ・センシティブ分類訂正の複数の自分投稿への反映は維持するが、公開後固定の利用条件には流用しない。

## D03 — quick-reaction

- **意図**: [I03](../product/social-experience.md#i03)。毎回選択画面を開かず、設定した絵文字で 1 操作リアクションする。
- **端末間の設定共有として採用済み**: [grill記録](../interviews/discord-feature-grill-2026-10-15.json)の`d03-q01-cross-device-quick-reaction`。
  同じ投稿用Profileでは常用絵文字設定を端末間で共通にし、別端末で再設定せず同じ絵文字を使える。
  異なるProfile間／Account全体への共有や、保存repo・APIを確定する決定ではない。
- **候補の状態**: 主要な利用意図は整理済み。設定保存／取得と技術・UX契約は設計／検証待ちで実装readyではない。
  candidate・queue未登録・issue未公開を維持し、実装packetへ自動昇格しない。
- **仮 slug**: `quick-reaction`。
- **target repo 別分割**: frontends の設定・投稿上のボタンを第一候補。
  端末間共有に必要な設定保存／取得契約を別候補へ分け、保存先repo・APIは設計する。ShuttlePubへの確定配置とはしない。
- **最小受付・検証案（未実施）**: 同じProfileの端末Aで設定すると端末Bでも共通設定が使え、毎回pickerを開かず1操作で反応できる。
  設定済み絵文字が1操作で送信され、未設定時や送信失敗時の状態が分かる。
  キーボード操作でも同じ導線を確認する。
- **依存**: 既存 reaction API、SNS UI の投稿表示。

## D07 — note-edit-federation

- **意図**: [I07](../product/social-experience.md#i07)。投稿を編集し、ActivityPub 互換性を考慮して変更を連合先へ反映する。
- **grillでの希望と技術確認**: [正規記録](../interviews/discord-feature-grill-2026-10-15.json)の

  ShuttlePubとの相互運用試験は未実施。詳細な根拠は正規記録に保持する。
- **履歴提供の採用方針**: `d07-q03-moderation-only-history`。一般閲覧者には編集した事実のみ表示し、
  旧本文・旧添付の履歴はモデレーション用途の閲覧権限を持つ人だけに提供する。一般画面だけ隠して
  一般APIから旧内容を取得できる状態にはしない。投稿者本人という理由だけで閲覧権限を付けない。
  履歴閲覧の画面・APIに権限確認を設け、投稿可視性・担当範囲と整合させる。非公開投稿の可視性を一律に拡張しない。
  一般閲覧の必要性とモデレーション用途を分ける当面の方針であり、公開済み情報の隠匿保証ではない。
- **履歴対象の採用方針**: `d07-q04-received-remote-history`。自鯖投稿に加え、受信した他鯖投稿についても
  自サーバーが受け取り把握した版をモデレーション用履歴に含める。未受信の全過去版の収集・常時同期は
  必須にせず、未受信版を変更なしと混同しない。一般UI/API非提供・モデレーション権限者限定を維持する。
- **旧添付保持の採用方針**: `d07-q05-old-attachment-content-retention`。取得できた旧添付は参照情報だけでなく
  ファイル本体も保持し、保持期間中は元配信先から取り外し・差し替えられても権限者が内容を確認できるようにする。
  未取得・取得不能と保持済みの実体は区別し、未取得ファイルの復元・完全保持や毎版の複製は決定しない。
  一般UI/API非提供・作者への自動権限なしを維持し、既存公開URLや外部キャッシュの消去・遮断は保証しない。
- **履歴保持期限の採用方針**: `d07-q06-bounded-history-retention`。通常の旧本文・旧添付履歴に保持期限を設ける。
  容量に加え、古い内容をいつまでも遡って扱われることを避けたい意図による。既定1〜3か月程度という希望を、
  `d07-q09-default-retention-30-days`で既定30日に具体化した。暦月単位の既定期間にはしない。
  現在の投稿の自動削除・古い投稿のモデレーション禁止・投稿編集期限へ拡大しない。具体的な共有実体の破棄方式も選ばない。
  `d07-q07-retention-per-superseded-version`で、各版が編集により旧版になった時点から期間を数え、
  旧版ごとに独立した期限を持つ方針を採用する。再編集で以前の旧版の期限は延ばさず、
  古い投稿でも新しい編集で生じた旧版は、その編集時点から保持する。
  `d07-q08-admin-adjustable-retention`で、通常の保持期間はサーバー管理者が短縮・延長とも可能とし、
  無期限設定は認めない。30日は管理者設定の上限ではなく、既定値を上限とする短縮専用や製品共通の固定期間にはしない。
  `d07-q10-retention-setting-prospective-only`で、設定変更は変更後に新たに旧版になる内容だけへ適用する。
  延長・短縮とも保存済み旧版の期限は不変とし、新たな旧版はその時点の設定期間を使う。
- **例外保全の採用方針**: `d07-q11-explicit-moderation-preservation`。調査に必要な保存中の版と保持済み添付を
  権限担当者が指定し、通常期限を超えて保全できる。他版の一括延長・通報だけでの全版自動保全・消去済み内容の復元は含めない。
  通常の保持期間設定・既存期限不変の方針とは区別する調査用の例外で、保全内容も一般UI/APIへは提供しない。
  `d07-q12-time-limited-reviewed-preservation`で、保全にも期限を設け、継続が必要な間は権限担当者が必要性を確認して更新する。
  調査未終了だけで期限なし・無条件自動更新にはしない。通常の30日を保全期間へ自動流用しない。
  `d07-q13-release-on-investigation-close`で、調査終了時にその調査を理由に指定した保全を解除する。
  保全期限の残りを理由に継続せず、別調査の有効な保全まで一括解除しない。保全解除と実際の削除は分ける。
  `d07-q14-return-to-original-expiry-after-preservation`で、その版の有効な保全がすべて解除・満了した後は
  元の通常期限に従う。期限内なら元期限まで残し、超過済みなら削除対象とする。追加猶予や通常期限のカウント停止・再開は設けない。
  別の有効な保全が残る間は保持を続け、履歴の削除対象化と共有実体の物理削除は区別する。
  リモートDelete受信済みの版の全保全終了後は、後述Q24の削除対象化を適用する。
- **保全期間の採用方針**: `d07-q16-preservation-30-days-from-confirmation`。標準期間は指定・必要性確認更新時点から30日後まで。
  通常期限や前の保全期限への積み増しではない。通常保持とは独立し、通常期間の設定変更で保全期間を自動変更しない。
- **共通の投稿削除・保持責務として採用済み**: `d07-q18-retain-unreported-deleted-posts`。
  [独立した意図の正本](../product/post-deletion-and-moderation-retention.md)で、自鯖作者の削除を一般表示へ反映しつつ、

  `d07-q20-retain-existing-revisions-after-deletion`で、自鯖作者削除後も保存済み編集旧版は元期限まで残し、削除で期限を変更しない。

  Accountの論理削除とも混同しない。固定commit・コード根拠は正規記録の`d07-q17-post-deletion-moderation-retention-boundary`を参照する。

- **候補の方向・状態**: 本文・添付の追加／差し替え／取り外し・CW・センシティブ指定を編集する主要な利用意図は整理済み。

- **編集前リポストの採用方針**: `d07-q27-keep-reposts-after-edit`。Q26とは独立に、元投稿の編集後も既存turboを維持し、変更後内容を表示する。
  再共有者の再確認を表示の必須条件にせず、編集後内容を確認・支持・再承認したとは扱わない。
  [D17](#d17)の内容同一性検証は調査候補として接続し、実装済み・peer検証済みとせず、旧本文・旧添付の一般公開も追加しない。
  取消し・削除・ブロック・モデレーション・閲覧権限等の別条件は維持する。
- **初回の編集通知として採用済み**: `d07-q28-include-edit-notifications`。編集済み表示に加え、後から変更を知り判断し直せる通知導線を含める。
  `d07-q29-edit-notification-audience`で、対象はその投稿をturbo・引用した人、またはその投稿に返信した人（OR）とする。
  いいね・絵文字のみの人は初期対象外だが、採用対象の操作もした人は後者の理由で対象になり得る。
  全フォロワー・既閲覧者・当該投稿への返信関係を持たないスレッド参加者全員へは拡大しない。
  自鯖で把握できる行動情報を前提とし、未把握外部行動の完全収集・全peer到達は保証しない。
  `d07-q30-coalesce-unread-edit-notifications`で、同じ受信者・投稿の未読編集通知がある間の再編集は1件へまとめ、最新編集を知らせる内容へ更新する。

  前期限に加算した80日目にはならないことを確認する。
  調査終了時にその調査の保全が解除され、残り期間を理由に継続しないこと、他の調査の保全解除とは混同しないことを確認する。

## D10 — sensitive-content-policy

- **意図**: [I10](../product/social-experience.md#i10)。閲覧注意の二択を越えて種類別に表示を選び、後からの変更も連合先へ反映したい。

- **分類の付与対象として採用済み**: `d10-q02-text-and-image-sensitive-categories`。
  画像ごとの分類に加え、本文にも同じ管理側の共通分類を付けられ、画像なしの文章投稿も対象とする。
  通常画像タグの本文自由タグ・hashtagへの拡張は含めない。
- **一部画像だけが該当する場合の範囲として採用済み**: `d10-q03-per-image-filtering-and-misskey-interoperability`。
  隠す分類が本文にはなく一部添付画像だけにある場合、該当画像のみ隠し本文と他画像は残す。
  本文と画像双方が該当する場合の表示統合・複数分類の優先／集約は別途設計する。
- **分類ごとの表示動作として採用済み**: `d10-q04-viewer-display-actions`。
  初回は「通常表示」「いったん隠し、押すと表示」の2段階。その場の表示ボタンも出さない非表示モードは初回外。
  通常表示はその分類による追加の非表示をしない意味に留め、他分類や投稿CWを自動解除しない。
  具体UI・解除の持続範囲や優先／集約は未決。
- **未設定利用者の初期値として採用済み**: `d10-q06-default-category-display`。
  既知の各センシティブ分類はすべて「いったん隠し、押すと表示」で始め、利用者は分類ごとに通常表示へ変更できる。
  既存の利用者設定の上書きを承認したものではなく、設定移行・新分類追加時・未知の外部分類ID・指定なしの内容までの動作は未決。
- **種類不明の外部指定用閲覧設定として採用済み**: `d10-q07-untyped-external-sensitive-preference`。
  「種類不明のセンシティブ」専用に通常表示／いったん隠し押すと表示を選べ、初期は後者とする。
  元の画像単位／投稿全体の指定範囲を区別し、通常表示でも独立したCW等を自動解除しない。投稿者が自由新設する分類や未知の外部分類ID・指定なしの内容の処理を決めたものではない。
  外部の`sensitive=true`をすべて全体指定とはせず、画像由来の集約と全体指定の具体的な解釈／写像は検証する。
- **本文だけが該当する場合と外部指定の区別として採用済み**: `d10-q05-text-only-filtering`。
  本文だけの分類が隠す対象に該当する場合、本文のみ畳み、画像は各画像の分類で判定する。
  外部の本文・画像全体への注意指定をこの本文分類に縮小して画像を露出させず、その指定範囲を区別して扱う。
  ただし外部の`sensitive=true`を一律に全体指定とはせず、Misskeyの画像由来の集約Note指定とも区別する。CW／投稿／attachment／情報欠落の写像・優先は設計・検証する。

  対象版・画像ごとの送受信・投稿全体CWとの優先・非対応peerへのfallback・後変更を調査／検証する。
  ユーザーが挙げた挙動を現行公式実装の確認済み事実や完全互換・相互運用検証済みとは扱わない。

## D13 — interaction-allowlists

- **意図**: [I13](../product/social-experience.md#i13)。投稿ごとに反応を許可する人を指定し、
  対象外の人にも許すアクションの範囲を選びたい。重要情報発信・企業公式アカウント等も想定する。
- **候補の状態**: 主要な利用意図は整理済み。連合契約は調査待ちで、互換性・技術契約の検証前に
  実装readyとはしない。candidate・queue未登録・issue未公開・仮slug未予約を維持する。
- **仮 slug**: `interaction-allowlists`。
- **target repo 別分割**: ShuttlePub の policy・投稿操作 / 受信時の適用契約候補、
  frontends の指定・反応可能状態の表示候補。必要時は Emumet の関係状態との接続を分ける。
  リスト追加枠の課金・認定とBooskiff課金連携は初回の必須依存にしない。
- **grillで採用済みの方針**: [正規記録](../interviews/discord-feature-grill-2026-10-15.json)を根拠とする。
  - `d13-q01-allowlist-subject` / `d13-q02-allowlist-selection`: 対象は人。
    個別指定と関係条件の両方を使い、対象外の人に許すアクションも別に設定する。
  - `d13-q04-list-reuse` / `d13-q05-initial-scope`: 許可専用の名前付き保存名簿は不要。
    個別指定と関係条件で先行し、タイムライン用リストの再利用は後続とする。
    その新規実装や契約の完了を初回提供の必須依存にしない。
  - `d13-q06-membership-evaluation` / `d13-q07-audience-union`: 条件と個別指定はOR。
    関係は反応時点の最新状態で判定し、どれにも該当しない人には対象外向けの操作設定を適用する。
  - `d13-q09-policy-mutation-decision`: 設定変更に期限を設けず、投稿元が新規操作の受理時に
    最新設定と関係状態で最終判定する。外部には変更を通知し、取得済み設定を事前表示に使える。
    毎操作の外部追加GETは正当性の必須前提にしない。古い設定から送られた操作にも投稿元の
    最終判定を適用し、自鯖の受理・通知・集計・表示を制御する。
    非対応peerの独自表示まで阻止する保証とは区別し、対応peer間の承認契約は別途詰める。
  - `d13-q10-existing-interactions`: 受理済みの返信・引用・リポスト・リアクションは維持する。
    許可設定や関係の変更で自動取消し・非表示・集計除外せず、過去の一斉再判定や取消し配信も行わない。
    最新判定は新規操作に適用する。同一activityの再送は冪等に扱い、設定変更だけで既存受理を覆さない。
    個別削除・通報・モデレーション・ブロック等の別機能の仕様は、この決定では変更しない。
  - `d13-q11-unrestricted-default`: 反応制限を未設定の投稿では、閲覧できる人に返信・引用・リポスト・
    リアクションをすべて許可し、通常の投稿に許可設定を必須としない。
    閲覧権限を追加したり、公開範囲・ブロック等の別の制約を解除したりはしない。
  - `d13-q12-allowed-audience-actions`: 制限を付けた投稿でも許可対象内の人には返信・引用・リポスト・
    リアクションをすべて許可する。操作別トグルは対象外の人にだけ適用し、対象内向けには設けない。
    この全許可も、閲覧権限・ブロック・モデレーション等の別の制約を解除しない。
  - `d13-q13-four-action-categories`: 対象外に許す操作は返信 / 引用 / リポスト /
    リアクション（いいね＋絵文字）の4分類とし、それぞれ独立したON/OFFトグルで選べる。
    いいねと絵文字には同じ許可を適用し、別々の許可設定は設けない。
    許可項目の共通化は、連合の通信形式や保存するリアクション情報の違いを失わせない。
    調査・提案の経緯は`d13-q03-action-toggles`に保持する。
  - `d13-q14-previous-post-settings`: 新規投稿の反応制限は前回の投稿の設定を引き継ぐ方向とする。
    投稿ごとの設定を引継ぎ元とし、別途アカウント既定値を編集・保存する手順を前提にしない。
    別管理のアカウント既定設定や名前付きプリセットを追加する承認ではない。
  - `d13-q15-settings-by-post-kind`: 通常投稿・返信・引用の3種類ごとに前回の反応制限設定を覚え、
    新規投稿には同じ種類の設定を引き継ぐ。返信の設定を次の通常投稿へ持ち越すなど、
    種類間で引継ぎ元を共用しない。
  - `d13-q16-initial-relationship-conditions`: 初回の関係条件は投稿者がフォローしている人・
    投稿者のフォロワー・相互フォローの3種類とする。相互は投稿者と操作する人の双方向のフォロー成立を指す。
    条件同士と個別指定の結合はOR、関係評価は新規操作の受理時点の最新状態とする方針を維持する。
    将来の条件追加を禁止せず、タイムライン用リストの再利用は後続のままとする。
  - `d13-q17-list-quota-billing-scope`: 原案の保存リスト枠3〜5個と追加枠の月額課金・公式認定は初回範囲から外す。
    この課金・認定やBooskiff課金連携を初回提供の必須依存にしない。原案は履歴として保持し、将来の採否は未決。
    3〜5を個別指定人数・投稿数・投稿種別の記憶枠・タイムライン用リスト等の上限へ転用しない。
    技術的な件数上限・レート制限・濫用対策の必要性や数値は別途設計する。
  - `d13-q18-restricted-outsider-default`: 引き継ぐ設定がなく初めて反応制限を有効にする場合、
    対象外向け4トグルはすべてOFFから始め、許したい操作を投稿者がONにする。
    制限未設定時と許可対象内の全許可は維持する。同種の前回設定があれば引き継ぎ、毎回OFFへ戻さない。
    履歴なしの新規投稿で自動的に制限を有効にする決定ではない。
  - `d13-q19-individual-list-visibility`: 個別に許可した人の一覧全体は他の閲覧者・peerへ公開・配布しない。
    操作する人には自分の反応可否を示し、投稿者は自分の一覧を確認・変更できる。
    明示的な一覧公開についての決定であり、操作結果等から対象者・関係を推測できない保証ではない。
    一覧を渡さずに可否を伝える方式は、変更通知・取得済み情報の事前表示・投稿元の最新判定と
    毎操作の外部追加GETを必須にしない方針と両立させる。
- **最小受付・検証案**: 対象と操作種別を明確にした policy 例で、reply / quote / turbo / reaction 等の
  許可・拒否を API と UI で一致させる。
- **連合契約の調査・検証が必要な事項（未実施）**: 4操作のpolicyと各peerの通信表現・承認方式の
  対応表を作る。更新通知の遅延・欠落・逆順、関係変更、設定変更と新規操作の競合、activity再送、
  受理結果の伝達をfixture等で検証する。非対応peerの独自表示が保証外であることと、一覧を配布せず
  本人の可否を伝えられること・未確認時の扱いも契約例で確認する。調査・検証の実施済みや実装packet化を意味しない。
- **依存**: 反応の各コマンド、Note 連合受信、認証・認可、最新の関係状態を参照する契約。
- **未決事項**: 「前回」に投稿成功・下書き・取消・投稿後編集のどれを含めるか、返信かつ引用の分類、
  端末間共有・保存場所・投稿画面への反映時点、制限切替時の一時設定保持・許可対象未選択時の扱い、
  フォロー申請中・ブロック等を含む関係状態の具体的な判定契約、関係条件ラベルの表示範囲・管理者の参照／監査、
  一覧を渡さず本人の可否を伝える通信方式・未確認／判定待ち表示、
  公開範囲・block/mute等との統合、policy表現・版管理・連合承認契約と
  非対応peerの詳細。後続タイムライン用リストの所有・公開・更新・再利用契約も未決。
  原案の絵文字だけ誰でも可、リポスト・いいねだけ可は履歴として保持するが、
  現在の許可モデルではいいねと絵文字を区別しない。
- **既存との関係**: 個人 block/mute とは別の投稿 policy 候補。
  [Booskiff のみを課金ポイントとする既存方針](../../booskiff/identity/mission.md) と
  SNS 機能の課金案の整合は将来再検討時の制約として保持し、今回その方針変更や課金実装を確定しない。

## D17 — turbo-content-verification

- **意図**: [I17](../product/social-experience.md#i17)。turbo した人が当時見た元投稿と、
  turbo を見る人に現在表示される投稿が同じ内容かを検証できるようにする。
- **比較対象として採用済み**: [grill記録](../interviews/discord-feature-grill-2026-10-15.json)の`d17-q01-comparison-content-scope`で、
  初回は本文・添付の内容・CW・センシティブ指定を比較対象とした。D07の編集範囲からの自動流用ではなく、今回独立に選択した。
  必要な内容・証拠を比較できない場合は確認不能とし、本文だけ一致して他項目が不明な場合を投稿全体の一致としない。
  添付URL／IDだけで内容一致は保証せず、具体的な証拠方式とpeer対応は調査待ちのcandidateとする。
- **確認不能時の新規リポストとして採用済み**: `d17-q02-repost-with-unverifiable-content`。
  必要情報が不足していても新規リポストでき、確認不能と識別する。情報不足だけで受付を拒否せず、同一保証や不正確認とも扱わない。
  通常の可視性・リポスト認可・削除・ブロック／モデレーション等の条件は維持する。
  署名不正・帰属矛盾等の積極的な不正根拠がある場合の無条件受付や、正当な編集差異の自動不正扱いへは拡大しない。
- **旧内容の保持終了後の検証継続として採用済み**: `d17-q03-persist-comparison-evidence`。
  旧本文・旧添付は既決の期限・保全・削除規則に従い、比較目的で期限を延長しない。
  比較に必要な情報だけを別保持し、リポストが残る間は検証を続けられることを製品意図とする。
  旧履歴の一般公開や削除／閲覧不可投稿の再表示は追加しない。比較情報の十分性・方式は技術検証待ち。
- **候補の状態**: 主要な利用意図は整理済み。方式・連合・表示・保持契約は調査／検証待ちで実装readyではない。
  candidate・queue未登録・issue未公開を維持し、実装packetへ自動昇格しない。次に接続先D10／D11の共通意図を確認する。
- **仮 slug**: `turbo-content-verification`。
- **target repo 別分割**: ShuttlePub の対象 revision / 内容 commitment・検証結果契約候補、
  必要時 Emumet の署名契約候補、frontends の同一・変更・検証不能表示候補。
- **最小受付・検証案（未実施）**: 本文・添付内容・CW・センシティブ指定それぞれの変更例と同一例で、
  同一性の確認結果と確認不能を区別する。本文が同じでも添付内容が変われば全体を同一と誤表示しない。
  削除／取得不能・署名を持たない外部投稿・添付内容や比較用情報が確認できない例を同一と混同しない。
  検証情報のない投稿も通常の条件を満たせば新規リポストでき、確認不能と識別されることを確認する。
  不正の根拠がある場合の受付や、後からの情報取得による状態更新の具体仕様はこの検証案で確定しない。
  必要な比較情報が得られる例では旧本文・旧添付を期限どおり削除した後も、残るリポストで比較を続けられることを確認する。
  添付を含め証拠が十分でない場合は確認不能とし、旧内容の期限延長や旧履歴一般公開・削除投稿再表示で補わない。
  具体的な証拠方式はこの検証案で確定せず、既存リポスト表示・一般旧履歴非公開・保持／保全期限を変更しないことも確認する。
- **依存**: D07 の revision / 更新モデル、turbo 基盤、Note 連合の識別・配送契約。
- **未決事項**: 元投稿の署名を載せる案の実現可能性、正規化と比較モデル・署名／内容commitmentの対象、
  添付実体と参照・順序・変換、CW／センシティブ指定のD10／D11共通契約、署名鍵変更、比較時点。
  再共有時の比較用情報を確保する方式、自他鯖／外部peerの対応範囲、情報不足と確認失敗の判定、状態名／UI／API、情報後取得時の状態更新、
  比較情報の形式・取得・十分性・寿命／削除、リポスト取消し・元投稿削除・共有参照・署名鍵変更との関係、一般への露出や照合の影響も技術検証する。
  旧内容の期限後も検証を続ける意図の採用は、復元不可・匿名性や全peerでの恒久検証を保証しない。HTTP 配送署名と永続的な内容証明を同一視しない。
- **既存との関係**: 既存 turbo を版と結び付ける拡張候補。D14 の IP 証跡とは独立して調査できる。
  D07の既存リポスト維持・最新版表示・再共有者の再確認／支持と扱わない方針を維持する。
  一般旧履歴の公開や比較を理由とする保持／保全期限の自動延長は追加せず、全peer対応や実装／相互運用検証済みとは扱わない。

  [Fedibird公式API](https://fedibird.com/api/v1/statuses/112635153227115367)で確認した。
  同じ投稿IDでも更新を処理しないpeerには旧版が残り、後からboostを受けるpeerには新版が届く例と、
  原投稿者が最初の内容で誘導して後から内容を変える可能性が論点。中継者による改ざんが起きた記録と読み替えない。
  [ActivityPubのUpdate](https://www.w3.org/TR/activitypub/#update-activity-inbox)は同じIDの表現の置換、
  [Announce](https://www.w3.org/TR/activitypub/#announce-activity-sharing)は再共有を扱う。
