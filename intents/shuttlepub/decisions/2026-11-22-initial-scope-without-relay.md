# 2026-11-22 リレーを初期の範囲から外し、投稿配送と転送の受け口から始める (D70)

2026-11-22 に operator と設計席の間で確定した決定。
[2026-11-22-timeline-routing.md](2026-11-22-timeline-routing.md) (D69) の続きで、番号を引き継ぐ。

## きっかけ

ShuttlePub の体験面を話す中で、operator が「以前の想定」と「今」を図で比べた。

- 以前の想定 (D43 ②・D44): Misskey などが ShuttlePub の relay actor をリレーとして登録し、
  公開投稿を送ってくる。ShuttlePub から見ると取り込みの入口。operator の評価は「これをいつ登録して
  もらうのか」「リレーというより Collector に近い」。
- 今: 相手は Emumet の Actor (Profile) を Follow する。ShuttlePub が Note を含む Create を作り、
  Emumet が宛先ごとに HTTP の署名を付け (ADR 0003 の署名 API、D57)、ShuttlePub が相手の inbox へ
  POST する (以下「投稿配送」)。relay actor はこの経路に入らない。operator の評価は「リレーサーバー
  としての機能は完全にサブだった」。

投稿配送の受け入れについて、operator が Mastodon・Misskey・GoToSocial の受信コードを読んだ結論:

- 3 実装とも条件付きで受理する経路がある。Actor・署名鍵・Activity の ID・Note の ID を Emumet の
  origin にそろえれば、ShuttlePub の送信元 IP が Emumet と一致しなくてよい。
- GoToSocial は Note の ID と `attributedTo` のホストが一致している必要がある (どちらも Emumet なので満たす)。
- 実機での受理・保存・フォロワーの TL 表示は未検証。

## 決定

| # | 決定 | 内容 | 状態 |
|---|------|------|------|
| D70 | 初期の範囲とリレー | (1) **呼び方**: 「リレーサーバー」を ShuttlePub 全体の呼び方から外す。外向きの経路は「投稿配送」と呼ぶ。外部の公開投稿を受け取る機能 (外から購読を受け付ける側・ShuttlePub が外部リレーに参加する側の 2 方式、仮称 Collector) と、受けた第三者の投稿を他サーバーへ配り直す機能 (再配信) は、投稿配送と分けて扱う。(2) **初期の範囲**: 取り込みの 2 方式と再配信は初期の範囲に含めない。外部リレーへの参加は認知を広げる選択肢として残し、投稿配送の相互運用を実機で確かめてから入れるかを判断する。再配信が要るかは未決。(3) **サーバー用 Actor**: 名前を system.actor とする (旧称 relay actor)。投稿配送には使わない。役割は D25 のコミュニティの actor、ShuttlePub が外部へ取りに行く署名付き GET の署名者 (リモート actor の公開鍵や親投稿の取得。GoToSocial は署名のない GET を拒む)、将来の外部リレーへの Follow の送り手。署名は ShuttlePub 自身の鍵で行い、Emumet は関わらない。(4) **P1 の最初の実行単位**: Emumet からの転送 (Producer ③) の受け口 (D39・D54・D68) とする。D48 の「Producer ② の受け入れを最初の単位にする」は取り消す。nitinol 0.8 と PostgreSQL の導入、まとまり「受け入れ」(検証・重複の除去) は ③ の受け口でそのまま使う。P1 の完了の目安 (D36) は ③ 経由なので変えない。(5) **Global TL**: 初期から持つ。材料は ③ で転送された、利用者がフォローしている外部ユーザーの公開投稿。フォロワー限定・ダイレクトはホーム TL・通知だけに出し、Global TL には入れない | 確定 |

## 投稿配送の相互運用テスト (外部リレー参加の判断材料)

Emumet と ShuttlePub を別のホスト・別の IP に置き、相手として Mastodon・Misskey・GoToSocial を
1 台ずつ立てる (連合 E2E の repo、D35)。各テストを 3 実装それぞれに対して行う。

| # | テスト | 確かめること |
|---|--------|--------------|
| T1 | 相手の利用者が Profile をフォローする | 相手が Emumet から Actor と公開鍵を取得でき、Emumet が返す Accept を受け入れる |
| T2 | ShuttlePub で公開投稿する | 送信元 (ShuttlePub) と署名者 (Emumet) が違っても、受け入れて保存し、フォロワーの TL に出る |
| T3 | 相手の検索欄に投稿の URL (Emumet のドメイン) を貼る | Emumet が ShuttlePub から中身を取って同じ URL のまま返し (透過プロキシ)、同じ投稿として表示される |
| T4 | 相手の利用者が T2 の投稿に返信する | Emumet の inbox からホームの ShuttlePub へ転送され (③)、通知やホーム TL に出る |
| T5 | ShuttlePub で投稿を削除する | 相手の画面から消え、その URL は Tombstone か 410 を返す |
| T6 | 署名の時刻を 5 分以上ずらして送る | Misskey が拒否する (テストが失敗を検出できることの確認) |

## 今回の決定に含めないもの (未決)

- **`shuttlepub-producer-intake` の扱い**。packet は queued (未公開) のまま。延期するか、③ の受け口の
  実行単位に作り替えるかは、次の実行単位を切るときに決める。
- **再配信が要るか**。要るなら何をどこへ配り直すか。
- **リレーが回してくる投稿の検証**。HTTP の署名者 (リレー) と actor (元の投稿者) が一致しないので、
  LD 署名を検証するか、Announce を開いて元の origin から取り直すかが要る。リレーを入れるときに検討する。
- **相互運用の未確認点**。Mastodon・GoToSocial の Date の許容幅、Note の `url` (HTML の表示先) を
  ShuttlePub に向けてよいか、Akkoma・Lemmy などほかの実装 (D41 の QA で広げる)。
