# 2026-11-22 Shared Inbox・転送の形・link の許可 (D71)

2026-11-22 に operator と設計席の間で確定した決定。
[2026-11-22-initial-scope-without-relay.md](2026-11-22-initial-scope-without-relay.md) (D70) の続きで、番号を引き継ぐ。

## きっかけ

ShuttlePub の体験面を話す中で、Emumet が外部の Activity をどこで受け、どの ShuttlePub に何を届けるかを
整理した。operator の整理:

- Emumet が Inbox (Shared Inbox) を持つ。外部の Activity を受け、宛先やフォロー関係から対象の Profile を
  割り出す。同じ ShuttlePub に複数の Profile がいれば、Activity の本体 1 件と宛先の Profile 一覧をまとめて送る。
- ShuttlePub は、アタッチのときの認可で成り立った信頼を前提に、宛先一覧を受け取って各 Profile の
  タイムラインに反映する。
- Emumet は外部の投稿を保存しない。ShuttlePub に転送して終わり (再送のための一時保管と D64 の隔離だけ)。

その過程で、link が「参加」「署名の許可」「受け取り」「コレクションの配布」「ID の名前空間」「世代」を
兼ねていて役割があいまいになっていることが分かり、許可を分け直した。

## 決定

### 受信と転送

1. **Shared Inbox**: Emumet は Shared Inbox を公開し (actor の `endpoints.sharedInbox`)、Profile ごとの inbox も残す
   (sharedInbox を使わずに個別に送ってくる実装がある)。どちらで受けても同じ流れにする。
2. **宛先の割り出し**: Emumet が行う。宛先は、投稿者をフォローしている Profile と、`to` / `cc` に書かれた Profile。
   D63 の除外 (Follow・Block と、既知の Follow・Block を確実に参照する Undo・Accept・Reject) はフォロー関係を
   持つ Emumet にしか判定できないので、Emumet が Profile ごとに判定し、除外した Profile は宛先に入れない。
3. **まとめて送る**: 送り先の ShuttlePub ごとに、Activity の本体 1 件と宛先一覧 (Profile の actor URL だけ) を
   1 回の要求で送る。P1 のうちに転送の契約 v1 を改める。D54 の「1 つの envelope に宛先の Profile は 1 つ」と、
   宛先の link ID・generation を外す。receipt は「1 回の受信 (Shared Inbox でも Profile の inbox でも)」とする。
4. **再送**: 単位は送り先の ShuttlePub (receipt × 送り先の origin)。1 回の送信が 2xx なら完了。各 Profile の
   タイムラインに反映するかどうかは ShuttlePub の中で決め、Emumet には返さない。重複除去の 2 段 (本体は
   Activity の `id`、宛先は `id` と Profile の組) は維持する。
5. **ダイレクト**: タイムラインとは分けた専用の画面 (Mastodon の非公開メンション、Misskey の DM のような見せ方) と
   通知で見せる。

### link の許可

6. **許可を分ける**: 信頼モード ①②③ の段階をやめ、次の 3 つを別々の許可にする。
   - (b) **署名**: ShuttlePub がその Profile として投稿してよい (署名 API、D57)。
   - (c) **受け取り**: 外部の Activity をその ShuttlePub へ転送する。ShuttlePub が求め、本人が許可すれば、
     その Profile 宛ての転送はすべて対象になる (D55 で P2 に持ち越した「② の link へは名前空間の投稿への
     返信・反応・リポストだけでよいか」には「いいえ、すべて」と答える)。
   - (d) **コレクション**: outbox などのコレクションの参照先と、ダイレクトの転送先。Profile ごとに 1 つの
     ShuttlePub だけが持てる。d は b を前提にする。
   c を求めず d だけを求めるサーバー (フォロー先の投稿は処理しないが、そのサーバーで書かれた投稿は outbox と
   して出す) もありうる。c でもダイレクトを部分的に許可できるようにする (範囲は未決)。
7. **「ホーム」という言葉を使わない**: 「ホームの ShuttlePub」「ホームの link」という言い方をやめる。
   ホーム TL は固有名詞として残し、c があれば作れる。Global TL も c で届いた公開投稿で作る (D70)。
8. **解除した後**: 過去の投稿は残す (Discord のサーバーで退会した人の投稿が残るのと同じ)。link の ID の名前空間と
   透過プロキシは解除後も続け、止めるのは署名と転送だけにする。削除は論理削除で、モデレーションで消すこともできる。
   解除後に消した投稿は、取りに来られたときに Tombstone を返すだけにし、Delete は送らない
   (解除後はその Profile の署名を使えないため)。
9. **d を移す**: d を別の ShuttlePub へ移すときは、同じ link のまま許可を変える。link ID (名前空間) は変わらないので、
   過去の投稿の ID と参照先もそのまま。outbox には d を持つサーバーで書かれた投稿だけを並べる。
10. **link のキャッシュ**: ShuttlePub は link をキャッシュしてよい。正本は Emumet のまま (D46 の「自分のモデルとして
    記録しない」を「正本にしない」に改める)。

- **転送の契約をどう改めるか** (v1 の revision にするか v2 にするか、要求と応答の形、Emumet 側の実装の直し方)。
  P1 の実行単位の設計で決める。Emumet 側は post-relay の C0〜I1 がマージ済みで、B1・T1 (`emumet-post-relay-e2e`)
  が進行中なので、そこへの影響を先に確かめる。
- **link の許可の持ち方**。D56 の「信頼モード (P1 は ③ だけ)」と「③ は Profile ごとに 1 つまでの DB 制約」を、
  b・c・d の許可と「d は Profile ごとに 1 つ」に置き換える方法。
- **c2 を許可したサーバーが複数あるときの見せ方**。フォロー先のフォロワー限定投稿も、c2 を許可したすべての
  サーバーに届く。許可の画面でそのことを本人に伝える必要がある。

## 補足: c2 (2026-11-22)

(6) の「c でもダイレクトを部分的に許可できる」の中身を、c の任意の選択肢 c2 として決めた。

| 許可 | 転送するもの |
|---|---|
| c (基本) | 公開・未収載の Activity と、Profile 宛ての公開の反応 (返信・Like・Follow など) |
| c2 (任意) | c に加えて、フォロワー限定とダイレクト (`to` / `cc` に Public を含まないもの)。自分がメンションされているフォロワー限定の返信も c2 に入る |

- ShuttlePub は「c だけ」か「c と c2」を求める。本人は c2 だけを断れる。
- c2 は c を前提とする。c を許可せず c2 だけ、という組み合わせは認めない。
- d は c2 を前提にしない。(6) の「c を求めず d だけを求めるサーバー」はそのまま認める。d が受けるダイレクトの
  転送は d 自身の役割 (D55、(6))。フォロワー限定は c2 を許可したときだけ届く。
  (当初は「d を持つサーバーは c2 を含む」と記録したが、同じ日に operator が「d は c2 を前提にしない」と改めた。)
- 振り分けは Emumet が `to` / `cc` に Public があるかで行う (宛先の割り出し (2) と同じ場所)。
- 未決の「複数のサーバーへ届くことの見せ方」で問題になるのは、c2 を許可したサーバーだけになる。
