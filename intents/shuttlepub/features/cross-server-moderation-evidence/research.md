# D14 サーバー横断モデレーション証跡 — 調査報告

調査日: 2026-11-18。設計調査のみ（実装・IP収集・運用試験なし）。正本は `packets/candidates.md` と `discord-feature-grill-2026-10-15.json` d14-q01〜q08。方式採用・実装readyではない。

## 結論

外部固定ログを用いる限定的方式を**継続調査**し、現時点で採用・IP保存開始はしない。投稿時点でランダムnonce付きcommitmentを独立追記専用ログへ固定し、事案ごとに自サーバー権限者が承認した場合のみ指定他サーバー担当者へIPと検証資料を渡す案が候補。IPそのもの・単純ハッシュの連合公開は不採用推奨。

この方式で示し得るのは後日提示値と当時のログ値の一致、及び記録欠落/改変の疑い。投稿元の初期虚偽、IPと人の対応、回線利用者、記録内容の真実性は証明しない。追記性はIP保存や越境開示の適法性も解決しない。

## 方式比較

| 方式 | 差し替え/欠落 | 鍵更新 | 平時プライバシー | 開示後照合 |
|---|---|---|---|---|
| DB内署名記録 | DBと鍵を一管理者が支配すれば履歴再構成可能。独立アンカーなしでは限界 | 鍵ID、有効期間、失効・漏えい時刻、旧鍵保存が必要 | IPは隠せるが署名対象/メタデータ注意 | 元記録・鍵が残れば可能。再生成との区別は困難 |
| IPハッシュ連合公開 | 変更追跡は可能でも初期値の真実性不明 | ハッシュだけでは署名鍵更新に対応しない | 候補IP辞書照合、投稿間横断照合。公開saltも候補試行可能 | 簡単だが共有/動的IPによる誤帰属、salt紛失/流出 |
| 外部追記専用ログcommitment | inclusion proofは掲載値、consistency proofは追記整合性を確認。提出済み欠落には独立受領記録が必要。監視者なしにログ分岐を排除できない | signing key更新、旧鍵信頼、checkpointと複数監視者照合 | 十分ランダムなnonceは辞書照合を軽減。時刻/件数等は漏れる | nonceとproofで照合。開示後の複製/再配布は防げない |
| 第三者暗号化保管/タイムスタンプ | 存在時刻の補助。欠落検知は契約/監査依存 | 暗号鍵と署名鍵を分離管理 | 保管者・鍵・アクセスログに依存 | 継続性が必要。第三者停止/漏えいリスク |

仮説は `C=H(domain||random_nonce||canonical_record)`。公開ログにはCと必要最小限の時刻のみ。本文・IP・安定ユーザーID・IP単純ハッシュは公開しない。投稿ごとに独立乱数を用い、投入受領記録を保持する。方式確定ではなく、ローカル署名＋定期checkpointを比較対照とする。

## 合成データ検証例（概念例、実装実行なし）

R1=`{post:urn:example:1, source:example.invalid, received_at:2030-01-01T00:00Z, ip:192.0.2.10}`、N1=`demo-random-01`、C1=H(domain||N1||canonical(R1))。例示値で実データではない。

* 一致: 後日R1/N1を提示、再計算C1とログinclusion proofが一致し、checkpointも監視者保存値と整合すれば「値が当時ログされた」と確認。
* 差し替え: IPを192.0.2.11に変えたR1'はC1'≠C1。元値/N1保全が条件。秘密紛失後は検証不能。初期虚偽や共謀は別問題。
* 欠落: 受領記録にC1と時刻があるのにinclusion proofがなければ未掲載/障害の疑い。受領記録もログもなければ未記録と消失を区別不能。

## 寿命・削除・保全

投稿存続中の検証可用性は目標だが、同一行/権限で無期限保存ではない。IP、nonce、原記録、proof、事案資料を別分類し、目的・必要性・アクセス主体・期限を個別定義。論理削除時は通常表示/APIから隔離し要求を記録。バッチ物理消去ではIP、対応表、nonce等を消し、バックアップ・索引・キャッシュ・監査ログの残存期限も決める。外部ログは通常消去困難ゆえ復元可能情報を載せない設計が重要だが、原記録を消せば後日照合不能にもなる。

調査中保全は通常保持と別フローとし、根拠、対象、開始/終了、承認者、再審査期限、閲覧記録、解除後消去を記録。削除済み投稿を自動延長しない。IPは動的/共有/NAT/プロキシ等のため単独で人を特定しない場合がある。D07の30日、D05の約5年は転用しない。

## 開示・認可・監査

q08に従い自サーバー権限者が事案ごとに承認。指定先担当者の身元/所属、目的、対象投稿、必要資料、期限を限定し、暗号化経路、受領確認、閲覧記録、再開示条件、訂正/誤送信対応を定義。担当者の指定/本人確認は未決。監査には事案ID、承認者、共有先、項目、時刻、根拠、期限、照合結果を残すが、監査ログへIP/本文を複製しない。開示後の複製・再配布を完全に防げるとはしない。

## 法的確認（適合済みとの結論なし）

運営地域・利用者所在地・処理主体・保管者所在地が未確定。IP/オンライン識別子の法的分類、取得/保存/開示根拠、目的限定・比例性・最小化、保存期限・消去要求、削除後保全と通知/異議、越境移転・委託契約・安全管理、侵害通知、アクセス/訂正権、未成年者、緊急/刑事開示手続、commitmentの再識別可能性を確認する。実データフローと地域確定後、専門家が判断する。

## 判断と次の調査

採用候補はnonce付きcommitment＋独立追記ログと、指定担当者への事案別共有。脅威モデル、ログ監視者の独立性、鍵更新/失効、削除整合、費用、法務評価が採用前提。不採用推奨はIP/単純ハッシュ連合公開、および単一管理者のDB/署名を改変不能証明と扱うこと。q07の平時照合困難性は望ましいが必須ではないため、残余リスクを明記して判断する。合成データのみで一致/差し替え/欠落/鍵更新/ログ分岐/秘密紛失を比較し、保持・複数運営者・担当者確認・開示手順をレビューする。成功しても本番IP収集の承認ではない。

## 出典

* ActivityPub, W3C Recommendation (2018-01-23): https://www.w3.org/TR/activitypub/ — サーバー間プロトコルで、IPや投稿者の実在を証明しない。
* HTTP Message Signatures, RFC 9421 (2024-02): https://www.rfc-editor.org/rfc/rfc9421 — 選択HTTP要素への署名。入力の真実性や接続元IPの証明ではない。
* Certificate Transparency v2, RFC 9162 (2021-12): https://www.rfc-editor.org/rfc/rfc9162 — Merkle log、inclusion/consistency proofと監視。掲載/追記整合性であり入力真実性ではない。
* RFC 6962 (2013-06、旧CT仕様): https://www.rfc-editor.org/rfc/rfc6962 — Merkle tree背景。現行参照はRFC 9162。
* RFC 8032 EdDSA (2017-01): https://www.rfc-editor.org/rfc/rfc8032 — Ed25519方式。鍵保護・失効・ローテーションは別設計。
* ActivityPub CG HTTP Signatures guidance（日付/更新履歴要確認）: https://swicg.github.io/activitypub-http-signature/ — 実装慣行で規範仕様ではない。
